# Privacy and limitations

## What ClearPacket does not do

- It does not write, alter, or generate any part of a scholarship application document.
- It does not determine legal eligibility — it surfaces discrepancies against what the official
  notice explicitly states, and leaves interpretation to the student and the issuing institution.
- It does not autonomously submit anything anywhere.
- It does not guarantee acceptance, and the product deliberately avoids any "application score"
  percentage or "guaranteed approval" language (see `docs/prompts.md` / Node 9 rules).

## Data handling

- **Private storage only.** Uploaded documents live in a private Supabase Storage bucket
  (`audit-documents`), never a public one. RLS policies on `storage.objects` scope every read,
  upload, and delete to `(storage.foldername(name))[1] = auth.uid()::text` — a user can only ever
  touch objects under their own UID prefix.
- **Strict RLS everywhere.** Every user-owned table in `supabase/migrations/0001_init.sql` has
  row-level security enabled and a `for all using (auth.uid() = user_id)` policy. There is no
  table a user can read or write outside their own rows via the anon/authenticated roles.
  `benchmark_runs` (evaluation output, not personal data) is the one exception: readable by any
  authenticated user, writable only by the service role from the offline eval CLI — never from
  the browser.
- **Server-side Gemini calls only.** `GeminiClient` (`lib/gemini/client.ts`) reads
  `GEMINI_API_KEY` from `process.env` and is documented to only ever be instantiated from
  server-side code (Server Components, Route Handlers, Server Actions, or the standalone eval
  CLI) — never a `"use client"` component. The key never reaches the browser bundle.
- **No service-role key in the browser.** `SUPABASE_SERVICE_ROLE_KEY` (`.env.example`) is
  server-only by convention and by the fact it's never referenced from `NEXT_PUBLIC_*`.
- **File validation.** Type and size are checked both client-side (fast feedback) and
  server-side (`lib/rule-engine/engine.ts` → `checkFileFormat`, backed by the same
  `allowedMimeTypes`/`maxFileSizeBytes` config the deterministic engine uses) — never trust the
  client-side check alone.
- **SHA-256 hashing.** `audit_documents.sha256_hash` is computed and stored for every upload, so
  duplicate/tampered-file detection doesn't require re-reading document contents.
- **No document contents in logs.** Server logs should log document *IDs* and structured
  metadata, never raw extracted text or file bytes. (Enforcing this is an application-level
  discipline — see "Known gaps" below.)
- **No applicant documents used for training.** This project makes no calls that opt documents
  into any model training pipeline; Gemini API calls are inference-only.
- **Redact sensitive fields from error reports.** Error paths should never include `rawValue`,
  `evidenceText`, or full document content in the message — only IDs and check names.
- **Revocable deletion.** Deleting an `audits` row cascades to every dependent table
  (`audit_documents`, `workflow_runs`, `requirements`, `extracted_facts`, `canonical_facts`,
  `findings`, `clarification_questions`) via `on delete cascade` in the migration. Deleting the
  Storage objects themselves is an application-level step (delete the audit row, then delete the
  matching Storage prefix) that should run in the same server action.
- **Rate limiting.** Not implemented in this codebase — flagged as a known gap below, with a
  concrete recommendation.

## Known gaps (honest, not exhaustive)

- **Rate limiting is not implemented.** For production use, add per-user rate limiting on the
  audit-creation and Gemini-calling routes (e.g. Supabase's built-in rate limiting, or a
  middleware-level token bucket keyed on `auth.uid()`).
- **Log redaction is a discipline, not a mechanism.** There's no automated scrubber verifying
  that a stray `console.error(someFinding)` doesn't leak `evidenceText`. A structured logger with
  an explicit allowlist of loggable fields would close this gap.
- **The RLS cross-user-access test requires a live Supabase project** to actually execute (see
  `tests/rls-cross-user-access.test.ts`) — it was not run against a live database in the build
  environment (no network path to `*.supabase.co`). A static check (also in that file) confirms
  every user-owned table has RLS enabled and a `user_id = auth.uid()` policy in the migration
  SQL, but that is not a substitute for a live integration test.
- **OCR/PDF text extraction quality is untested against real scanned documents** in this build —
  see `docs/evaluation.md`.

## Disclaimer

ClearPacket is a decision-support tool, not legal, financial, or admissions advice. Findings are
generated by an AI workflow and, despite the verification and evidence-citation design described
in `docs/workflow.md`, can still be wrong. Always confirm with the official scholarship notice
and the issuing institution before acting on any finding, especially anything marked `critical`.
