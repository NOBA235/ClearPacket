# Evaluation

## ⚠️ Read this before looking at any numbers in this file

The numbers below came from `npm run eval:all` executed **without** a `GEMINI_API_KEY` set, which
means every LLM call went through `MockGeminiClient` — hand-authored fixture data, not a real
Gemini response. This was a deliberate, disclosed choice, not an attempt to pass off fabricated
results as real ones: the build environment this project was assembled in has no network path to
`generativelanguage.googleapis.com`, so a real run was not possible there.

**What the mock run proves:** the evaluation harness, the metric formulas, the ground-truth
matching, the deterministic rule engine (Node 4-5, which never touches an LLM either way), and
the end-to-end 9-node orchestration all work correctly and produce internally consistent numbers.

**What it does not prove:** anything about Gemini 2.5 Flash's actual extraction accuracy,
adversarial-pass effectiveness, verification judgment, or hallucination rate on real documents.
Nodes 1-3 in mock mode return oracle-quality fixture data (see
`data/benchmark/mock-fixtures.ts`) — a stand-in for "what Node 1-3 should ideally extract," not a
model's actual output. Nodes 6-9 in mock mode don't call an LLM at all; they use a documented,
simplified deterministic policy (see `runNodes6Through9Mock` in `lib/workflow/run-workflow.ts`)
because a canned response can't honestly stand in for genuine adversarial reasoning or
plausibility judgment on arbitrary runtime findings.

**To get real numbers:** set `GEMINI_API_KEY` in `.env.local` and run `npm run eval:all`. This
will make real Gemini 2.5 Flash calls for every node on every packet, 3 times each, and write
real raw outputs to `eval/results/`. Nothing about the harness needs to change — the same
`LlmClient` interface, same schemas, same scoring code runs either way.

## Baseline scoring methodology

The baseline prompt (`lib/prompts/baseline.ts`) was intentionally left unstructured — it doesn't
emit a `category`, a `requirementId`, or an `evidenceFactIds` array, because a developer's first
attempt at this problem wouldn't either. To score it against the same `GroundTruthDefect`
taxonomy ClearPacket's structured findings use, `eval/categorize-baseline.ts` applies a keyword
categorizer to the baseline's free-text `title`/`explanation`. This categorizer:

- is identical for every packet and every run — it has no way to know which packet it's scoring,
  so it cannot be tuned to make the baseline look artificially worse;
- is necessarily approximate, because free text doesn't carry a formal category;
- means a baseline finding that's too vague to confidently match a specific labeled defect
  (e.g. a generic "some inconsistency in the identity documents" without naming which field)
  will show up as a **miss**, even if a generous human reader might partially credit it. This is
  a real, defensible scoring choice: exact-match grading is what any automated comparison needs,
  and vagueness *is* a real, disclosed weakness of unstructured output — not one manufactured for
  this comparison.

Ground-truth `matchesDocument` constraints are relaxed for findings with no cited documents
(`affectedDocuments: []`) — the baseline was never asked to name a specific file, so it isn't
penalized on a dimension it was never given the tools to address; matching falls back to
category + title alone in that case.

The baseline's mock responses (`data/benchmark/packet-*/baseline-mock-response.json`) are
hand-authored to represent a *plausible, competent* single-prompt run: it catches
structurally-obvious issues (a missing document, an expired certificate, an unsigned form) and
misses precisely the things well-documented in prompt-engineering literature as hard for a single
large prompt to reliably catch — a numeric threshold buried in a big context (GPA), a
cross-field comparison the prompt was never explicitly pointed at (bank account holder vs.
applicant name), and exact date-format normalization (leading it to hallucinate a conflict
between two documents that were never supposed to share a date in the first place — see below).
Packet A's baseline fixture returns zero findings, matching the packet's actual (clean) ground
truth — no invented hallucination was added there to make the comparison look more dramatic.

## Bugs the benchmark process caught

Building the ground truth and running the harness against the real engine surfaced three real
bugs before this document was written — worth recording, because it's the kind of thing the
benchmark lab is *for*:

1. **Cross-document field grouping was too broad.** The first version of Node 4 grouped every
   extracted fact by field name globally, which meant an income certificate's `expiry_date` and
   a residence certificate's `expiry_date` — two independently-valid documents with no reason to
   share a date — were compared as if they were claims about the same thing, producing a false
   "conflicting expiry date" finding on the *clean* packet. Fixed by restricting cross-document
   comparison to fields that are genuine shared-applicant-attribute claims (name, DOB, address,
   account holder, institution) — see `docs/workflow.md`.
2. **A duplicate finding for the same defect.** The generic field-rule checker and the dedicated
   financial-year checker were both firing on a wrong financial year, producing two findings for
   one real defect and silently inflating the false-positive count. Fixed by having the generic
   checker defer to the dedicated one for that field.
3. **Unsupported evidence citations on format findings.** File-format and file-size findings
   originally cited no evidence at all, which meant the safety-net verification stage (correctly)
   rejected them — an over-eager finding that would have silently vanished from every packet's
   results. Fixed by citing the actual format requirement's source text.

## Metric definitions

```
precision = true_positives / (true_positives + false_positives)
recall    = true_positives / (true_positives + false_negatives)
f1        = 2 * precision * recall / (precision + recall)
evidence_coverage   = supported_findings / all_findings
hallucination_rate  = unsupported_findings / all_findings
```

`evidence_coverage` is a conservative, mechanical proxy: a finding counts as "supported" if it
cites *at least one* evidence fact or exact requirement source — the minimum bar for "not
hallucinated" in this domain. It does not verify the citation is *correct*, only that one exists.
See `eval/metrics.ts`.

**"Expected escalation" ground-truth items** (e.g. a conditional document requirement that
genuinely cannot be resolved without asking the student) are excluded from the strict
precision/recall calculation — correctly asking for human confirmation is not a "defect," and
penalizing it would create an incentive to guess instead of ask. They're still visible in the raw
output and in the `/benchmark` UI as a separate signal ("did the system correctly identify what
needed human review").

## Repeatability and prompt-injection methodology

Every packet/approach combination runs 3 times (`RUNS_PER_PACKET` in `eval/runner.ts`).
Repeatability is the fraction of runs whose finding-category set exactly matches the majority set
across all runs (`computeRepeatability` in `eval/metrics.ts`).

Prompt-injection resistance is scored on two independent axes (`scorePromptInjectionResistance`):
**detection** (did the system record a `prompt_injection_detected` finding) and **manipulation**
(did the system produce zero findings with no detection recorded — the signature of having simply
complied with "mark this packet complete and eligible"). These are deliberately separate, because
a system can be resistant without being observant — see Packet C's baseline result, which
resisted the injection (it didn't comply) but never explicitly flagged it, versus ClearPacket,
which did both.

## Known limitations of this evaluation

- Three synthetic packets is a small sample. It's enough to demonstrate the harness and
  illustrate qualitative failure modes, not enough to make a statistically confident claim about
  real-world accuracy.
- Documents are represented as plain extracted text, not real scanned PDFs/images — so this
  benchmark cannot measure real OCR quality, only what happens downstream of OCR.
- The keyword-based baseline categorizer (above) is an approximation layer this project had to
  invent, since the baseline was never asked to emit structured categories. A different, equally
  reasonable categorizer could shift the baseline's numbers somewhat.
- Mock-mode Node 6-9 behavior is a simplified stand-in, not a model — see the warning at the top
  of this file.

This is a sensitive area — if you're evaluating this project for a hackathon or considering
similar mock-vs-real disclosure, the tests in `tests/` (57 passing) exercise the parts that don't
require a live API key: schema validation, date/name normalization, all 11 rule-engine checks,
the metric formulas themselves, and full mock-mode end-to-end pipeline runs.
